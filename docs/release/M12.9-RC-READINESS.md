## Critical runtime-flow finding

The repository currently exposes learner/instructor read APIs, instructor formative guidance, and AI coaching. The canonical practice/project verification journey is proven at service/database test level, but the production API/runtime tree does not currently expose a complete learner submission → verification-dispatch path, and there is no executable trusted worker/BullMQ runtime in `apps/worker`.

This is **not classified as a deployment-only gap**. Shipping an RC while the authoritative flow can only be driven by test/service harnesses would violate the M12 release blocker rule “critical flow unusable”.

M12.9 therefore must not hide this as operational debt. Before RC creation, the project needs one of:

1. evidence that the production runtime path exists elsewhere in the locked implementation and was omitted from the recovered repository; or
2. a formal Change Review allowing the relevant already-LOCKED implementation milestone(s) to be reopened solely to complete production runtime wiring, without changing domain authority or product semantics.
